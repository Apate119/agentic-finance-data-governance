# Output Guide

## Overview

This document explains the primary output files generated by the Agentic Finance Data Governance Pipeline.

The pipeline produces outputs across four areas:

* Data quality results
* Governance scorecards
* Exception-level exports
* Remediation tracking

These outputs are designed to show how data quality control results can be converted into governance-ready reporting and actionable remediation workflows.

## Data Quality Results

### `outputs/data_quality/quality_check_results.csv`

This file contains the raw results from each automated data quality control.

Each row represents one control execution.

| Field | Description |
| --- | --- |
| run_timestamp | Timestamp when the control was executed |
| control_id | Unique control identifier |
| check_name | Name of the data quality check |
| table_name | Table evaluated by the control |
| dimension | Data quality dimension such as completeness, validity, or integrity |
| severity | Severity of the control |
| failed_count | Number of records that failed the check |
| status | PASS or FAIL |

### How to Interpret

A control with `status = PASS` means the failed count was zero.

A control with `status = FAIL` means one or more records violated the rule and may require remediation.

## Governance Scorecards

### `outputs/scorecards/governance_scorecard.csv`

This file provides an executive-level summary of the full pipeline run.

It is intended to answer:

* How many controls passed?
* How many controls failed?
* What was the overall pass rate?
* Were any high-severity controls breached?
* Is the dataset ready for regulatory reporting?

### Key Fields

| Field | Description |
| --- | --- |
| total_controls | Total number of controls executed |
| passed_controls | Number of controls that passed |
| failed_controls | Number of controls that failed |
| pass_rate | Percentage of controls that passed |
| failed_records | Total number of failed records across all controls |
| high_severity_failures | Number of failed high-severity controls |
| medium_severity_failures | Number of failed medium-severity controls |
| regulatory_readiness_status | Overall readiness assessment |

### How to Interpret

A status of `Ready` means no high-severity issues were identified.

A status of `Not Ready` means one or more high-severity issues were identified and should be remediated before the dataset is considered reporting-ready.

## Enriched Data Quality Results

### `outputs/scorecards/dq_results_enriched.csv`

This file joins raw data quality results to the control inventory.

It adds governance metadata such as:

* Control description
* Data owner
* Regulatory relevance

### Why It Matters

Raw data quality results are useful for technical review, but enriched results make the output more useful for governance stakeholders.

This file connects each failed control to the business owner and regulatory reason it matters.

## Exception Summary

### `outputs/scorecards/dq_exception_summary.csv`

This file summarizes failed controls using governance metadata.

It is useful for quickly reviewing:

* Which controls failed
* Which owners are responsible
* Which issues are high priority
* Which failures have regulatory relevance

## Exception-Level Exports

### `outputs/exceptions/*.csv`

These files contain the actual failed records for selected controls.

Examples include:

| File | Purpose |
| --- | --- |
| `customer_name_null_exceptions.csv` | Customer records missing customer names |
| `invalid_country_exceptions.csv` | Customer records with invalid country values |
| `invalid_account_status_exceptions.csv` | Account records with invalid account statuses |
| `orphan_account_exceptions.csv` | Account records not linked to valid customers |
| `orphan_transaction_exceptions.csv` | Transaction records not linked to valid accounts |
| `null_regulatory_balance_exceptions.csv` | Regulatory balance records missing reported balances |

### How to Interpret

Exception files are intended for detailed remediation review.

A data owner could use these files to identify the exact records that need correction, investigation, or escalation.

## Exception Export Summary

### `outputs/exceptions/exception_export_summary.csv`

This file summarizes which exception files were created.

It provides a quick inventory of exported exception outputs and the number of failed records included in each file.

## Remediation Action Log

### `outputs/remediation/remediation_action_log.csv`

This file converts failed controls into remediation actions.

Each row represents an issue requiring review or remediation.

| Field | Description |
| --- | --- |
| control_id | Failed control identifier |
| check_name | Name of the failed control |
| table_name | Impacted table |
| dimension | Data quality dimension |
| severity | Severity of the issue |
| priority | Remediation priority |
| failed_count | Number of failed records |
| owner | Assigned data owner |
| regulatory_relevance | Governance or regulatory impact |
| remediation_status | Current remediation status |
| target_resolution_days | Expected resolution timeframe |
| recommended_action | Suggested action for the owner |
| created_timestamp | Timestamp when the remediation item was created |

## Priority Logic

| Priority | Criteria | Target Resolution |
| --- | --- | ---: |
| P1 | High severity failure | 2 days |
| P2 | Medium severity with 100+ failed records | 5 days |
| P3 | Medium severity with fewer than 100 failed records | 10 days |
| P4 | Low severity or informational issue | 15 days |

## Reviewer Guidance

A reviewer should start with the outputs in this order:

1. Review `outputs/scorecards/governance_scorecard.csv` for the executive-level readiness status
2. Review `outputs/scorecards/dq_exception_summary.csv` to understand which controls failed
3. Review `outputs/scorecards/dq_results_enriched.csv` to see ownership and regulatory relevance
4. Review `outputs/exceptions/*.csv` to inspect failed records
5. Review `outputs/remediation/remediation_action_log.csv` to understand remediation ownership and priority

## Summary

The output layer demonstrates how technical data quality checks can be converted into governance-ready artifacts.

The outputs support executive reporting, issue triage, exception review, and remediation tracking.
